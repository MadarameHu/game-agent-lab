# 游戏任务轨迹展示前端 PRD

版本：v1.1 · 日期：2026-09-20 · 状态：供设计与开发使用的需求稿

范围：平台跳跃、城市建造、赛车各 4 个，共 12 个 case，包含此前完成的 racing-01 赛道重排。

依据：现有 11 个批量 case 与独立 racing-01 的本地产物及审阅页面，重点核对 racing-04 的需求、来源、验收契约、执行命令、行为结果，以及 racing-03 的失败和修正记录。本文件描述后续前端，不代表以下功能已经实现。

## 1. 产品定义

建设一个能让非游戏开发者读懂的「游戏任务过程与结果工作台」。用户打开一个任务，既能看到效果，也能理解：从什么场景出发，使用什么素材和环境，agent 改了什么，为什么判定通过，失败后如何修正，以及最终是否被人接受。

页面的基本单元是一条可追溯的任务链路：

**需求 → 初始场景与素材 → 执行产物 → 评测契约 → 验证记录 → 反馈与修正 → 最终候选 → 人工决定。**

这条链路用于阅读和导航；实际时间顺序另外记录。例如，评测契约通常在实现前冻结，不能因页面把它放在执行产物之后就暗示评测标准是事后制定的。

### 1.1 用户与核心问题

| 用户 | 需要回答的问题 | 页面支持 |
| --- | --- | --- |
| 对游戏感兴趣、不了解技术的项目负责人 | 让它做什么？实际改出了什么？我能试玩吗？ | 白话概述、前后画面、素材卡、试玩入口 |
| 数据与研究负责人 | 这条数据为什么被接受？能追溯失败和修正吗？ | 标准与证据关联、候选版本、来源和接受状态 |
| 执行或验证开发者 | 哪个文件、哪个检查出问题？怎样复现？ | 改动清单、差异、测试步骤、参数、日志和环境 |
| 人工审阅者 | 哪些已测、哪些仍需我判断？ | 覆盖缺口、待体验清单、绑定具体版本的审阅表 |

### 1.2 第一版成功标准

1. 未参与开发的人在一个任务详情页内，能找到需求、输入素材、执行环境、产物、标准、方法、结果、修正和最终效果。
2. 任意一个「通过」都能追溯到具体检查、适用候选版本与证据；无法关联时明确标注证据不足。
3. 有记录的失败能够追溯到后续修正产物及复验；缺失历史不被补写成完整轨迹。
4. 人工决定与自动结果分开展示，未审阅始终显示待审阅。
5. 12 个 case 全部接入同一列表、详情结构和统计：平台跳跃 4 个、城市建造 4 个、赛车 4 个。racing-01 的数据适配属于 P0 必做，不以独立旧页面链接替代接入。

设计走查可邀请 3 位未参与实现的人，分别回答上述问题。目标是每人 3 分钟内定位信息，查看指定检查的原始证据不超过两次点击。这是拟定的产品验收目标，不是已有测试成绩。

### 1.3 本期范围

P0 完成现有数据的结构化展示、证据导航、候选版本阅读、最终效果和人工审阅；优先保证信息真实、易读、可追溯。

本期不包含自动执行调度、自动部署模型、训练 reward model、经验检索 harness、云端游戏串流或自动重跑修复。前端可保存修改反馈，但不能让用户误以为点击「需要修改」已经触发新一轮 agent。

## 2. 现状与问题

当前页面已有任务卡片、需求正文、初始和最终截图、自动检查列表、JSON 折叠面板、试玩和人工决定。已有数据足以支持第一版，但组织方式有以下问题：

| 现状 | 造成的理解障碍 | 新版处理 |
| --- | --- | --- |
| 原始需求、输入素材和保留项藏在同一份 JSON | 用户难以看出初始能力和本次新增能力 | 分成需求、初始状态、素材、修改边界 |
| 检查显示英文 ID 和 pass | 不知道标准是谁定的、到底测了什么 | 中文标题、标准来源、方法、实测值、证据 |
| 执行结果主要以截图体现 | 容易把场景代码修改误解为图片生成 | 明确展示脚本、场景、参数与资源变化 |
| manifest.attempts 存放多个命令 | 导入、测试、截图可能被误读为多次生成 | 区分候选版本、命令运行和反馈事件 |
| agent 身份只有概括说明 | 容易误以为独立 reward model 已参与 | 分开记录角色、系统、模型与实际调用证据 |
| 顶层统计只有通过数量 | 不知道是否覆盖全部要求或经过人审 | 自动检查、覆盖情况、记录完整性、人审分开 |
| 失败证据在各自目录内 | 看不到失败如何影响下一次修正 | 提供反馈与修正的关联时间线 |

特别注意：输入 task.json 保留了准备阶段的 status 和 evaluation_status。它描述当时的输入状态，不能覆盖执行后的 manifest/result，也不能直接显示成当前任务状态。

## 3. 信息架构

两级页面即可满足第一版，避免拆成多个需要来回寻找的后台模块。

### 3.1 任务总览

- 顶部：项目名称、批次、任务数、筛选后的任务数、最近更新时间。
- 统计：已有候选、自动检查通过、待人工、人工要求修改、人工接受；标明统计分母和所属批次。
- 筛选：平台跳跃／城市建造／赛车；自动状态；人工状态；有失败记录；历史不完整。
- 搜索：任务标题、ID、需求关键词。
- 卡片：代表图、任务标题、一句话目标、改动摘要、当前候选标识、自动与人工状态、是否有修正记录。
- 主操作：「查看完整过程」；次操作：「试玩当前候选」。

无最终截图时使用明确标注的「初始场景」缩略图，不伪装成生成效果。卡片不显示跨任务平均 reward 排名，因为任务难度、标准和覆盖不同。

### 3.2 任务详情

采用「顶部摘要 + 左侧章节导航 + 中央阅读区 + 按需证据抽屉」。

| 导航 | 主要回答 |
| --- | --- |
| 任务概览 | 做什么，现在做到哪一步了？ |
| 需求与边界 | 哪些是显式要求，哪些必须保留？ |
| 输入场景与素材 | 开始时有什么，可用什么？ |
| 环境与参与者 | 在哪里运行，谁执行、谁定标准、谁验证？ |
| 执行与产物 | agent 交付了什么，改了哪些文件？ |
| 评测标准 | 怎样才算完成，标准来自哪里？ |
| 验证方法与结果 | 实际怎么测，证据支持什么结论？ |
| 反馈与修正 | 哪次失败，改了什么，复验如何？ |
| 最终效果与人工验收 | 当前候选长什么样，能否接受？ |

默认显示最终候选。在页头切换历史候选后，产物、验证、媒体同步到所选候选；需求或契约发生变化时明确显示其对应版本，不能把最新版通过结果贴在旧候选上。

### 3.3 桌面布局示意

```text
任务库 / 赛车 / racing-04                    当前候选 [最终候选 ▾]
把摩托车接入主场景并支持停车换车             [试玩此候选]
自动检查通过 · 人工待审阅 · 历史记录部分完整
一句话：接入已有摩托车，并实现停车时切换黄色卡车。

章节导航       主内容                                      证据抽屉（点击后）
概览           [初始画面]          [当前候选画面]             检查：停车换车
需求与边界     本次新增 / 原有能力 / 仍待人工判断             对应需求 R-02
输入与素材     ……                                          操作、期望、实测
环境与参与者                                               原始 JSON / 日志
执行与产物                                                 候选与校验器版本
评测标准
验证与结果
反馈与修正

```

使用连续文档阅读，不把每个字段都做成卡片。证据抽屉用于深入查看单项信息，关闭后保留滚动位置。手机端导航收为章节选择器，抽屉变全屏；完整代码差异以桌面体验为主。

## 4. 模块详细需求

### 4.1 任务概览（P0）

展示标题、ID、类别、目标一句话、当前候选、最新结果时间、自动验证与人工状态。用「原来／这次改动」两列概括差异，例如原来启动只有黄色卡车，这次默认摩托车且停车时可切换。

摘要下提供初始／最终画面，不能只用大幅最终图占满首屏。关键提醒以短句呈现，例如「多次换车测试预设了停车状态；实际手感待你试玩」。

若当前已人工拒绝，首屏显示拒绝原因与对应候选；后续产生新候选后，新候选显示待审阅，旧拒绝决定仍保留。

### 4.2 需求与修改边界（P0）

分四部分：原始 query、拆分后的需求、保留条件、禁止或限制的修改范围。

每条需求拥有稳定 requirement_id。卡片显示：白话要求、原文出处、来源、关联产物、关联检查、覆盖状态。点击需求即可跳到对应验证。

来源至少支持：

- 原始任务文本中的显式要求。
- 初始工程或任务包声明的保留条件。
- 规则设计者增加的可执行解释，例如「接近静止」被解释为速度小于 0.5 m/s。
- 后续人工反馈新增的要求。

来源不能凭语义推测成确定事实。当前 task.query_origin 说明需求为此集合编写，页面应称为「原始任务需求」，不标成论文原始标注或逐字用户原话。

需求覆盖状态：已关联自动检查、待人工判断、部分覆盖、未覆盖、无法确认。它与检查执行状态不同：某个脚本通过，不代表该条需求的所有部分都测到了。

### 4.3 初始场景与输入素材（P0）

初始场景展示入口、原有功能、原有实体、已知缺口、初始画面和工程来源。首屏用中文名称解释资源类型，不要求用户先理解 .tscn、.glb 等后缀。

素材区默认只列任务相关素材，提供「查看完整清单」。每项展示名称、用途、类型、文件路径、来源／许可证、是否可修改，以及本次使用状态。

| 展示例 | 类型 | 在任务中的作用 |
| --- | --- | --- |
| 摩托车模型 | 3D 模型 | 外观资源；来源为原工程随附模型 |
| 摩托车场景 | 预配置游戏对象 | 组合控制器、模型和声音 |
| 摩托车控制脚本 | 代码 | 原有侧倾、前叉及车轮表现 |
| 摩托车发动机声 | 音频 | 原有专用发动机音效 |
| 原赛道 | 场景／地图 | 应保留的可驾驶环境 |

使用状态包括：任务可用、实际引用、被修改、新增、未确认使用。不能把 available_assets 中的每个文件都标成实际被模型使用。

P0：图片缩略图、音频播放、资源名称和路径、出处链接；没有预览时显示类型图标与「尚无预览」。P1：3D 模型旋转预览、资源依赖图、场景树。没有新增模型时，应明确「复用了输入素材」。

### 4.4 引擎、环境与参与者（P0）

环境与 agent 分开展示，避免把引擎当模型，或把测试脚本当验证模型。

环境字段：引擎与版本、物理后端、渲染后端、运行位置、操作系统／硬件（有记录才展示）、入口场景、输入方式、关键测试参数，以及启动方式。

区分「上游声明配置」「本次实际执行配置」「尚未验证配置」。本案例上游声明 Godot 4.6 / Forward Plus，本轮 runtime 记录验证 Godot 4.7.2 / gl_compatibility；不能用上游配置代替实际运行信息。行为测试的 60 FPS 参数从运行记录展示，不推断所有测试都相同。

参与者表包含：角色、执行主体、系统／模型 ID、输入、输出、工具、记录完整性。

角色至少支持执行 agent、规则设计者、程序验证器、交叉审查者、人工审阅者。角色与模型不是一一对应；同一模型可以承担多种角色，程序验证器也可以完全不调用模型。

当前资料仅能确认使用 Codex agents，未另行调用独立 reward model。若具体模型 ID、请求参数、原始响应未记录，显示「未记录」，不能从当前会话配置反推历史调用。验收规则、测试代码由 agent 编写，与专门训练的 reward model 分开标注。

### 4.5 执行过程与模型输出（P0）

执行输出按四类展示：

1. **游戏产物**：修改后的工程、场景、脚本、材质、参数等。
2. **改动说明**：改了什么、服务哪条需求、哪些原能力保留。
3. **可观测执行记录**：已保存的动作、命令、退出码、耗时和日志。
4. **模型调用原始记录**：只有真实保存时才展示 prompt、可公开响应和工具调用；未保存就显示缺失。

工程差异与检查器差异分区，避免让用户把新增测试代码看成游戏功能。文件列表展示新增／修改／删除，点击可看文本差异；二进制资源提供前后预览或哈希。历史基线不可得时只能显示现有文件，标明无法重建差异。

展示公开的计划摘要、动作和结果，不需要或声称提供模型内部推理。没有记录的中间计划不得事后生成并冒充原始输出；可以补写面向读者的解释，但须标为「后补说明」并保留作者与日期。

每个候选关联来源输入、父候选、生成角色、产物哈希和对应标准版本。导入、测试、渲染属于该候选下的运行记录，不自动新增候选编号。

### 4.6 评测标准与 reward 设计（P0）

默认标题为「怎样才算完成」，技术视图显示 criterion、checker 和 reward 配置。

| 字段 | 说明 |
| --- | --- |
| 判定项 | 可读标题和稳定 ID |
| 关联需求 | 能回到原始要求及出处 |
| 来源与制定者 | 用户显式要求、保留规则、agent 的解释或人工补充 |
| 可执行标准 | 操作条件、阈值、单位、容差、边界 |
| 类型 | 硬性条件、软评分、人工判断 |
| 检查方式 | 静态文件、运行状态、真实输入、模型评估或人工 |
| 校验器 | 代码路径、版本／哈希；有模型调用时记录模型与提示模板 |
| 冻结与变更 | 标准版本、冻结时间、变更原因 |
| 已知限制 | 不能由此标准证明的事情 |

racing-04 示例：「接近静止」来自任务文本；速度 < 0.5 m/s 且驱动状态 < 0.08 是本次契约采用的技术解释。界面必须让用户看出两者区别。

reward 单独提供解释面板，显示记录值、适用候选、聚合公式或配置出处、参与的检查项、人工部分是否缺失。当前 engine_reward=1 展示为「本任务记录的引擎奖励：1」，旁边说明自动硬性检查通过；若原始记录没有统一公式定义，公式栏显示「未记录」，不能事后构造权重并说成实际计算过程。

若未来增加模型软评分，必须同时显示评分范围、评判输入、模型版本、解释和调用证据。人工未评时 human_review 和 combined_reward 保持空，不显示成 0 或 1。跨 case 的同分不等于同等质量。

### 4.7 验证方法、实测结果与证据（P0）

主表以需求或判定项为行，建议列为：判定项、标准、实际方法、实测结果、状态、证据。默认仅显示易读短句，详情在抽屉展开。

每条验证至少能回答：在什么初始条件下，执行了什么动作，观测哪个对象，期望多少，实际多少，由哪个检查器判定，在哪个候选上执行。

验证方法允许多个标签同时存在：静态检查、真实运行、输入事件、预设状态、截图、模型评判、人工试玩。例如「真实 Tab 输入 + 预设停车状态」可同时出现，不能简化为「完整玩家试玩」。

预设状态（fixture）要用白话解释，如「测试开始前把车速设为零，用于单独检查换车功能」。说明它排除了哪些因素，也指出未验证什么，例如没有因此证明自然制动到停车的全过程。

证据抽屉包含：

- 对应需求与标准，标准和候选版本。
- Given／When／Then 的中文描述：起始条件／操作／预期。
- 实测值、单位、阈值、容差和逐项断言（原记录有才显示）。
- 截图、视频、JSON、日志、运行命令和环境参数。
- 输入或位置注入方式、覆盖限制、结果产生时间。
- 原始文件入口，以及哈希一致／未核验／不一致状态。

状态必须区分通过、失败、检查运行错误、未运行、不适用、证据缺失、证据过期。退出码为 0 但含 SCRIPT ERROR 时，不能仅按退出码标绿。脚本解析失败属于验证执行错误，不能自动描述为游戏玩法失败。

原则：需求、标准和实际检查允许多对多关系。racing-04 契约有 5 个硬性条目，而最终结果有 11 个检查；不能依靠 ID 相等强行一对一连接。经过核对的映射记录来源；未能确认的保持未关联。

### 4.8 失败反馈与修正（P0）

用时间线展现有证据的事件：生成候选、验证失败、审查发现、发送反馈、修改产物、修改检查器、复验、人工决定。

每次修正卡包含：失败现象、诊断依据、反馈来源、反馈原文或已保存摘要、修正主体、父候选、改动差异、新候选、复验结果、仍存限制。只保存了修复文件但没保存交回 agent 的消息时，显示「反馈传递文本未记录」。

区分四类事件：产品修正、检查器修正、评测标准变更、环境修正。它们不能统一记成「模型失败一次」。测试脚本修正后即便游戏工程未变，也会生成新的验证运行记录，并保留旧检查器与旧结果的绑定。

历史回填规则：文件名 v1/v2、命令数组顺序和文件修改时间只能作为线索，不能自动推断真实生成顺序。有明确时间／父子关系时按记录展示；其他归入「历史证据，顺序未确认」。只保存局部旧文件时可以查看局部差异，不提供完整旧版本试玩。

标准改变后旧结果继续保留在旧标准下；新标准对当前候选需重评，不继承旧的通过状态。

### 4.9 最终效果、试玩与人工决定（P0）

最终效果包括初始／最终并排图、可用额外视角、视频（存在才显示）、对应候选、捕获环境和操作方式。

媒体必须标注：实际引擎渲染或其他来源、游戏默认相机或审查相机、静态画面或行为片段、是否使用测试状态。不同机位截图默认并排，不启用容易误导的滑块叠图；相机一致时再提供叠图比较。

试玩入口显示「在本机 Godot 打开此候选」，状态包括准备副本、导入资源、启动中、已打开、失败。明确从哪个候选启动，以及存档是否隔离。无法连接本地启动器时提供运行说明，不能显示启动成功。过往未完整保存的候选禁用试玩并说明原因。

人工检查表来自契约中的 human_checks，例如摩托车手感、换车镜头连续性、HUD 可读性。支持逐项接受／需修改／未检查及备注；旧数据只有总体决定时显示原样，不虚构逐项记录。

提交操作：「接受此候选」「需要修改」。提交时展示所审候选和简短决定摘要，拒绝要求填写具体问题。审阅结果绑定候选哈希和标准版本；页面停留期间候选变化则拒绝陈旧提交，提示刷新。保留意见草稿。

提交后明确提示「人工决定已保存」。需要修改时不自动声称 agent 已接单；本期显示「反馈已保存，尚未发起修正」。已保存决定不静默覆盖；新版本另行审阅，纠正误提交需追加更正记录。

## 6. 数据组织与接口契约

### 6.1 建议的数据实体

前端使用统一视图数据，保留原始文件作为证据。不要让各个 UI 组件分别猜测不同 case 的历史格式。

| 实体 | 关键字段 |
| --- | --- |
| Task | id、title、category、query、query_origin、requirement_ids、input_snapshot_id |
| Requirement | id、text、source_kind、source_ref、preservation、coverage_state |
| InputSnapshot / Asset | id、来源、版本、资源路径、类型、许可证、预览、哈希 |
| Environment | engine、version、renderer、physics、host、参数、declared_or_observed |
| Actor | id、role、system、model_id、身份来源、记录完整性 |
| Candidate | id、parent_id、task_version、artifact_refs、project_hash、actor_id、created_at |
| ExecutionEvent | id、type、candidate_id、actor_id、time、input_refs、output_refs、命令／动作 |
| Criterion / Contract | id、version、requirement_ids、标准、阈值、来源、制定者、冻结记录 |
| VerificationRun | id、candidate_id、contract_version、checker_hash、environment_id、状态 |
| CheckResult | id、criterion_ids、verification_run_id、方法、fixture、expected、actual、status、evidence_ids |
| Feedback / Revision | id、source、针对的候选或检查、问题、后续候选／校验器、复验引用 |
| Evidence / Media | id、路径、类型、哈希、来源、捕获模式、camera_mode、候选、时间 |
| HumanReview | id、candidate_hash、contract_version、逐项结果、总体决定、备注、时间、作者 |

这是产品所需的字段模型，不要求第一版引入数据库。可用归一化 JSON 加轻量服务实现。

缺失值统一用 null 并附 missing_reason（未采集、原文件缺失、不适用、尚未运行）；不要用空字符串或 0 混用。重要字段记录 provenance：来自原文件、人工核对映射或后补说明。

### 6.2 现有文件映射

| 现有来源 | 新版用途 | 处理要求 |
| --- | --- | --- |
| catalog.json 与 racing-01 元数据 | 总览列表与分组 | 合并两个来源，按唯一任务 ID 去重计数；本次应为 12 |
| task.json | 需求、初始状态、素材、边界 | 准备阶段状态不作为当前状态 |
| source.json | 工程出处、许可证、上游环境 | 区分上游声明与实际验证 |
| runtime.json / commands | 本轮引擎和运行方式 | 不补造未记录硬件或参数 |
| project/ | 当前候选产物 | 与测试代码分开显示 |
| contract/acceptance.json | 标准与人工检查范围 | 保存冻结版本；标准到检查需显式映射 |
| contract/baseline-hashes.json | 基线与保留性证据 | 哈希本身不能重建旧文件内容 |
| evidence/final/result.json | 检查总表、reward、限制、哈希 | 保留原始 ID，中文解释不能改变含义 |
| behavior.json 等 | 细项测量和 fixture | 合并到具体检查，不与总表重复计数 |
| evidence/root-review.json | 交叉核验及完整性 | 显示为 agent 审查，不标作人审 |
| manifest.json | 当前状态与命令摘要 | attempts 不等同于候选数或修正数 |
| trajectory.jsonl | 阶段事件 | 缺少时间或动作的地方标记不完整 |
| 历史日志、脚本和截图 | 失败／修正证据 | 不以文件名自动确立版本顺序 |
| human-review.json | 人工决定 | 与自动结果分开、绑定候选 |

racing-01 的源目录为 `outputs/racing-01-run/`，其 manifest、轨迹、验证器与证据布局有所不同。适配器单独映射到上述统一实体，保留原始数据及已有人工决定；不要求为了统一页面而重跑任务或改写历史。原独立页面可保留为兼容入口，主工作台中必须有完整详情。

### 6.3 第一版数据缺口

需要补的是「展示适配数据」与「未来采集字段」，两者分开处理。

现在可核对补充：中文标题与说明、需求拆分、素材类型、标准与检查的关联、现有证据索引、已保存改动差异、来源标签。

历史上未保存就不补造：精确模型 ID、每次模型调用 prompt/response、完整工具调用序列、tokens／成本、每次完整候选快照、未记录的失败反馈文本、逐动作视频。

后续运行应原生采集候选快照、标准与校验器版本、事件时间、反馈关联、模型调用元数据和媒体来源。PRD 中的历史完整性标签使现有 case 无需等待这些字段齐全即可展示。

### 6.4 建议接口（目标，非当前已实现）

- `GET /api/tasks`：分页／筛选后的任务摘要，不返回完整文件哈希和日志。
- `GET /api/tasks/:id`：需求、素材、参与者、版本摘要与当前状态。
- `GET /api/tasks/:id/candidates/:candidateId`：产物、差异、标准、验证与效果引用。
- `GET /api/tasks/:id/events`：带来源与顺序可靠性的事件。
- `GET /api/evidence/:evidenceId`：受约束的文件／片段读取，日志可分页。
- `POST /api/play`：输入 task_id、candidate_id，返回运行状态；沿用当前运行副本与独立存档策略。
- `POST /api/reviews`：输入候选哈希、契约版本、决定与备注；服务端重验完整性和版本一致性。

当前 `/api/state` 可在迁移期保留，由适配器输出新视图模型。不要把任意本地路径或任意 shell 命令开放成前端操作；试玩与证据读取限定已登记产物。外部展示时不暴露 API 密钥、环境变量和不必要的本机绝对路径。

## 7. 状态、异常与交互规则

### 7.1 状态分层

页面内部维护独立状态，避免只用一个「完成」标签：

| 维度 | 状态示例 |
| --- | --- |
| 执行 | 未开始、执行中、候选已生成、执行失败 |
| 验证 | 未运行、运行中、通过、失败、运行错误、证据不完整、过期 |
| 人工 | 未审阅、接受、需修改 |
| 完整性 | 一致、未核验、不一致 |
| 历史 | 完整、部分记录、无过程记录 |

首屏归纳状态必须保留原始维度。例如「自动通过 · 人工待审阅 · 历史部分记录」。发现候选文件变化后，已有通过标为「对应旧文件版本」，禁止按旧证据提交新的人审接受。

### 7.2 异常处理

| 情形 | 预期表现 |
| --- | --- |
| 无模型身份记录 | 显示 Codex 系统和「模型 ID 未记录」，不隐藏整段 |
| 标准有条目、无检查映射 | 标记未确认覆盖，提供原始标准 |
| 证据文件缺失或哈希不同 | 警示证据不可用／不一致，不继续呈现为可信通过 |
| 测试未运行或出错 | 显示未运行／运行错误，不计入通过 |
| 无历史修正记录 | 显示未记录修正，不推断一次成功 |
| 没有视频或模型预览 | 显示已保存截图／资源信息，不使用假播放器 |
| 服务断开 | 保留已读内容并提示状态可能过期，禁用提交和启动 |
| 试玩启动失败 | 显示导入或启动阶段及日志入口，允许用户重试 |
| 人审过程中版本变化 | 保留草稿，要求切换到新版本重新核对 |
| 刷新或切换章节 | 保留筛选、所选候选、滚动位置和未提交意见 |

## 8. 视觉与可读性要求

- 默认简体中文。需求解释、过程叙述、动作目的、输出说明、判定依据、验证方法、结果解读、失败诊断、修正说明和验证限制均以中文呈现。不能只翻译导航而把主体过程保留为整段英文。
- 专有名词（如 Godot、Codex、reward、fixture）、模型名称、技术 ID、代码、API 字段、文件名、路径、执行命令和原始日志保留原文，不强行翻译。必要时在首次出现的术语旁提供简短中文解释。
- 执行命令保持原样，命令旁的「执行目的、输入、输出、结果」用中文说明。原始模型响应和断言可保留原文，默认过程视图提供忠实中文说明，并可展开查看原始证据。
- 中文说明保留原有数字、单位、阈值、否定条件和不确定性；后补翻译或解释标注为展示说明，不伪装成执行时的模型原话。
- 主层讲需求、动作和结果；代码、完整路径、哈希、命令进入第二层。
- 通过／失败／待定同时用文字、图标与颜色表示，不能只靠红绿。
- 动态刷新只更新变化区域，不打断阅读、代码选择或输入。
- 表格提供清晰列标题；按钮支持键盘操作、可见焦点和明确可访问名称。
- 图像附任务和视角说明；正文不以截图内小字承担关键信息。
- 页面保持「当前任务、当前候选、当前标准」上下文，证据抽屉中也可见。
- 不显示没有来源的置信度、自动生成进度百分比或装饰性成功统计。

## 9. 优先级与交付顺序

| 优先级 | 交付 | 验收代表 |
| --- | --- | --- |
| P0-1 | 数据适配和信息架构；需求、素材、环境、角色、产物、缺失标签 | racing-04 可回答全链路基本问题 |
| P0-2 | 标准与检查映射、方法／实测／证据抽屉、reward 解释 | racing-04 的 5 个契约条目与 11 个结果正确关联 |
| P0-3 | 反馈修正时间线、版本绑定、校验器变更区分 | racing-03 可追溯前瞻方向修正；平台跳跃测试修正不冒充产品修正 |
| P0-4 | 媒体对照、正确候选试玩、人工决定、总览筛选 | 全部 12 项可浏览并审阅，含 racing-01，无伪造缺失记录 |

## 10. 可执行验收清单

1. racing-04 详情能直接读到原始需求、初始缺口、9 项声明素材、保留条件与实际环境。
2. 角色区准确表明使用 Codex agents、无独立 reward model；缺失具体模型 ID 不填猜测值。
3. 执行区分开显示游戏产物与校验器，不将三次命令执行显示为三次模型生成。
4. 标准表把「接近静止」与 `<0.5 m/s` 的解释区分，阈值有出处。
5. 多对多关联保留契约的 5 个硬性条目及最终 11 项检查，不遗漏或重复计算。
6. 反复换车检查显示真实 Tab 输入和预设停车状态；证据可打开原 JSON 与校验器。
7. 驾驶实测显示约 7.364 m／1.5 s，与当前原始行为记录一致；未记录的实测值显示未记录。
8. racing-03 可看修正前后脚本及对应复验，无法恢复的旧工程不显示可试玩。
9. 校验器修正单独记录；标准变更不继承旧标准下的通过结论。
10. 额外审查相机截图和默认游戏相机截图有明确标注；无视频不显示可播放入口。
11. 全部 12 项的自动结果与各自真实人工状态分开展示；reward=1 不转换成「人工已接受」，也不覆盖已有人工决定。
12. 试玩启动绑定所选候选，资源导入失败可见，存档隔离规则可读。
13. 候选在验证后变化时，旧结果标记过期或不一致，旧人审表单不能接受新文件。
14. 人工反馈保存后可读且不可静默覆盖；「需要修改」不假称已启动修复。
15. 输入状态、缺失模型数据、无历史、日志错误、服务断开等异常均有对应显示。
16. task、candidate、criterion、check 和 evidence 支持稳定深链接，刷新后可恢复位置。
17. 总览从去重数据计算，共 12 个任务，每类各 4 个；racing-01 与其他任务使用同一详情结构，来源批次仅作为次要元信息。
18. 代码与媒体按需加载；首屏不加载全部日志、完整资源树或全部哈希。
19. 12 个任务的默认中间过程均可用中文读懂；专有名词、代码和执行命令保留原文，英文原始记录可按需展开。抽查需求、验证和修正说明，数值及条件须与原始证据一致。

## 11. 交付物要求

前端开发阶段交付：统一数据适配说明、页面布局与组件、现有 case 的关联索引、只读证据接口、试玩／人审兼容接口，以及上述清单的验证记录。

本 PRD 不要求先建设完整 harness。第一步是把已有任务讲清楚，使用户能看懂并核对一条数据为什么被接受；随后再用同一数据契约接入更完整的执行流水线。
